# Adoption and Distribution Brief — Skills Manager

**Version 1.1.0**

**AI manifest:** Current DEL-11 proof story, migration guide, installation
claims, and design-partner brief. Facts and verification commands are dated
September 20, 2026; this document does not invent user, download, or usability
metrics.

## One-sentence position

Skills Manager is the local control plane for AI-agent skills: it shows which
physical copies exist, validates what agents may load, and makes sync,
rollback, and trust evidence reviewable from one loopback UI.

The differentiator is control and evidence — filesystem truth, explicit
targets, observable divergence, validation, provenance, and recovery — not a
claim that a skill is safe merely because it is popular or fetched from a
registry.

## Migration from manually managed roots

The safe migration path preserves existing agent directories and starts
read-only:

1. Install the published package with `pip install skill-control-plane` or
   `pipx install skill-control-plane`.
2. Run `skills-mgr scopes` and `skills-mgr list --scope all` to inventory roots
   and physical instances. Do not delete or move a manually managed root.
3. Use the web UI's logical Library and Instances views to inspect duplicates,
   disabled documents, malformed documents, and divergent content.
4. Add or create one canonical skill in the global store only after reviewing
   its validator output, then use the existing explicit `sync NAME --from
   global --to SCOPE` operation for each intended target.
5. Run `skills-mgr doctor --scope all` and keep the generated export/backup
   before any cleanup. Trash and snapshots remain recoverable through the
   existing workflows.

The manager does not silently adopt every root, infer precedence, delete a
project, upload skill bodies, install a credential helper, or start an update
daemon. Agent-scope writes go to the selected filesystem root; SQLite remains
rebuildable index state.

## Proof story and reproducible evidence

The short demonstration should show these four states in the current build:

| Scene | Proof | Reproducible procedure |
|---|---|---|
| Logical Library | Same-name copies collapse into one row while physical instances remain visible | Seed two scopes with identical and divergent `SKILL.md` files; run `python3 browser_harness.py` and inspect the Library/Instances states |
| Effective-state evidence | Consumer/root evidence stays cited and unresolved when precedence is undocumented | Run `skills-mgr doctor --explain CONSUMER --project DIR`; use the Workspaces view for adapter/project observations |
| Quality and trust | Validation, advisory risk evidence, registry hash/cache state, and provenance are visible without a safety claim | Run `skills-mgr validate NAME`; use Install → Registry; review the returned `inspection`, `_registry`, and `registry_provenance` fields |
| Recovery | Mutations target one physical instance and history/trash/snapshots provide rollback | Edit, disable, sync, remove, restore, and inspect History in a hermetic disposable data dir |

The repository's automated viewport evidence is generated by
`python3 browser_harness.py` at 320, 400, 640, 900, and 1280 px. It reports
console/runtime/network failures and overflow. For dated local PNG evidence,
pass `--screenshots-dir <directory>`; the harness writes one labeled
`viewport-WIDTHxHEIGHT.png` file per probe. This does not fabricate human
usability or adoption results. Screenshots used in external communication
must be captured from that current build, dated, and labeled with the build and
viewport rather than presented as historical product evidence.

## Installation and release claims

Verified local distribution claims on this tree:

- Python 3.10+ and a stdlib-only runtime;
- `pip install skill-control-plane` / `pipx install skill-control-plane` as
  the published package path;
- `skills-mgr webui --no-browser` starts the loopback UI, with the canonical
  bind at `127.0.0.1`;
- the optional `desktop_launcher.py` is unbundled, loopback-only, and not a
  replacement for the canonical CLI/UI;
- CI and package-data checks govern artifacts; optional local artifact coverage
  remains unavailable when `python3 -m build` is not installed.

No claim is made here about popularity, safety certification, hosted sync,
team signing, automatic updates, download volume, retention, or human
activation until those claims have their own dated evidence and decision.

## Design-partner brief

**Cohort:** five to eight consented users who maintain skills across at least
two agent consumers; include both a novice-to-skills-manager operator and an
expert who already maintains multiple roots. This is a recruitment target, not
completed participant evidence.

**Pilot workflow:** inventory roots → inspect the logical Library → validate a
skill → sync one exact target → deliberately create a divergent copy → review
the evidence → restore from history/trash. Registry fetch, hosted backup, and
team governance are optional discussion topics, not required pilot promises.

**Data handling:** use synthetic or user-owned skills with written consent;
capture task outcomes, observed errors, viewport, date, and environment only.
Do not collect skill bodies, prompts, credentials, telemetry, or remote account
data. Participants can inspect and delete the disposable fixture directory.

**Success signals:** a participant can identify the physical target, explain a
divergence, complete validation, and recover a mutation without an operator
intervening. Record failures and uncertainty; do not turn this into a fabricated
conversion percentage.

**Exit conditions:** publish only after the protocol, consent form, de-identified
notes, and dated screenshots are reviewed. Stop the pilot if a mutation target
is ambiguous, a recovery path is unclear, or the UI suggests that popularity or
registry origin is proof of safety.

## Open gates

Git/review/apply seam does not authorize a new package runtime, a public bind,
