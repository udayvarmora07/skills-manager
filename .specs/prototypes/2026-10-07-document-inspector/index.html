First-principles production software engineering methodology for building, debugging, testing and shipping. You MUST use this before writing non-trivial code.

When to use this

Before writing non-trivial code. Before debugging. Before optimising. Reach for the underlying mechanism rather than the pattern you were given last time.

What "Divergent" means here

Seven copies of this file exist on disk, and they are not the same file. Three different content hashes are in play, so codex and opencode are reading one set of instructions while gemini is reading another. This tool will not pick one for you — see the Copies panel on the right.

Principle 1 — the mechanism is the thing

When you reach for a familiar pattern, ask what makes it work. If you cannot answer, you are cargo-culting. The answer is usually a constraint you have forgotten about: an invariant the runtime maintains, a property the type system is enforcing, a failure mode the queue is designed to absorb.

Principle 2 — measure before you change

A change made without a measurement is a guess with extra steps. Establish the current behaviour first, with something that would fail if the behaviour changed. Then change one thing.

  1. Reproduce the current behaviour in a check that fails when it regresses.
  2. Change exactly one thing.
  3. Re-run. If it does not move the number you were trying to move, revert and rethink.
Why this matters for a skills file

A skill is loaded into an agent's context, not read by a person under review. If the instructions disagree between copies, the agents silently disagree with each other — and there is no error, because each one is faithfully doing what its own copy says.

Principle 3 — delete before you optimise

Most performance work is removing work. Measure where the time actually goes before making it faster; a large fraction of "slow" code is doing nothing at all.
